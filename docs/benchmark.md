# 压测报告：WebSocket 弹幕下行链路

> **先说前提**：以下所有数据都在 WSL2 单机上测得，压测端和服务端抢同一份 CPU、同一个内核网络栈。
> 这些数字只适合做**同条件下的前后对比**，不能当成绝对容量。真实容量要等两台云机器复测（见第 9 节）。

---

## 1. 结论速览

本轮只做了一项优化：**WritePump 合并写**（newplan III.8）。改前改后参数完全相同：3000 连接 / 10 房间 / 每连接 0.5 msg/s / 90 s。

| 指标 | 改前（每条消息写一次） | 改后（取空队列，多条合成一帧） | 变化 |
|---|---|---|---|
| 丢失率 | 7.43% | **0.01%** | 几乎归零 |
| 运行中掉线 | 12 | **0** | |
| 延迟 p50 / p95 / p99 | 2001 / 7598 / >10000 ms | **138 / 266 / 455 ms** | p50 降低 93% |
| 下行投递 | 37.8 万次/s（跟不上需求） | **44.7 万次/s（= 需求）** | |
| 服务端 CPU（30 s 采样） | 153.8 s（512%） | 116.8 s（389%） | −24% |
| write 系统调用 CPU（`Syscall6` flat） | 85.0 s（占 55%） | 55.6 s（占 47.5%） | −35% |
| 平均每次 write 带几条消息 | 1 | 2.9 | |

一句话结论：**瓶颈是"每条消息一次 write 系统调用"，不在业务逻辑。** 合并写让每次调用的固定开销被多条消息分摊，系统从"处理不过来"回到"处理得过来"。所以 CPU 只降了 24%，延迟却降了一个数量级（原因见 4.4）。

加压到 5000 连接 / 10 房间（每房间 500 人）后，数据如下：下行 114.9 万次/s，丢失 0.51%，p50 423 ms，平均每次 write 带 4.07 条消息。消息量涨到 2.6 倍，write 的 CPU 只涨到 2.2 倍，说明合并写让写成本随负载**次线性**增长。

## 2. 环境与方法

### 2.1 环境

| 项 | 值 |
|---|---|
| 机器 | WSL2，20 核，单机 |
| 部署 | server 与 `cmd/benchmark` 同机，走 loopback |
| 资源争用 | server 和 benchmark 各占约 500–650% CPU |
| 服务端配置 | `config.yaml` 默认值：Kafka 异步落库 + 1 秒聚合器，未开 `legacy_*` 实验开关 |
| 限流 | 服务端每连接弹幕 2 条/s（突发 5 条）；压测速率 0.5 条/s，不会触发限流 |

### 2.2 压测工具 `cmd/benchmark`

自己写的（Go + gorilla/websocket），流程如下：

1. 用 admin 账号登录、建房、开播（开播接口是幂等的，可以重复跑）。
2. 用 `-jwt-secret` 在本地签发 N 个不同 `user_id` 的 token，不走注册接口。
3. 按 `-ramp`（默认 200 条/s）逐步建连，第 i 条连接进房间 `i % rooms`。
4. 全部连上之后，每条连接按 `-msg-rate` 发 chat，`content` 里写入发送时刻（纳秒）。
5. 收到带自己前缀的 chat 时，用 `now − 发送时刻` 算出端到端延迟。
6. 停止发送后再等 `-drain` 秒收尾，然后出报告。

**指标定义**（报告里的每个数都按这里的口径算）：

| 指标 | 定义 |
|---|---|
| 下行投递（次/s） | 客户端收到的 chat 总数 ÷ 发送阶段时长。**这是扇出计数**：一条上行消息投给房间里 300 人，就算 300 次，不是 300 个独立请求 |
| 期望接收数 | Σ(每个房间的发送数 × 发送开始时该房间的连接数) |
| 丢失率 | 1 − 实收 ÷ 期望。中途掉线的连接收不到后面的消息，也算进丢失，这符合用户视角 |
| 延迟 | 发送端写入内容的时间戳 → 接收端解析出来的时刻。两端同机、共用时钟；换成跨机器要先对时 |
| 延迟直方图 | 每 1 ms 一个桶，不存原始样本（几千万个样本会吃掉几百 MB）。超过上限的全部落进最后一个桶，所以"> 10000 ms"表示被截断 |

### 2.3 服务端观测点

| 来源 | 用途 |
|---|---|
| `live_ws_messages_total{direction="down"}` | 服务端视角的下行投递数，和工具的 received 对账 |
| `live_ws_dropped_total{reason="client_slow"}` | 某条连接的 Send 通道满了，服务端主动丢弃的消息数 |
| `live_ws_write_batch_size` | 每次 write 合并了几条消息，是合并写生效的直接证据 |
| `live_broadcast_duration_seconds` | 一次房间广播（`deliver`）的耗时 |
| `:6060/debug/pprof/profile?seconds=30` | CPU 火焰图 |
| `:6060/debug/pprof/heap` | 堆内存 |

⚠️ Prometheus 计数器是**进程累计值**。每轮压测前必须重启 server，否则这一轮会叠加上一轮的数（第 5.1 节就吃过这个亏）。

### 2.4 复现命令

```bash
# 在 backend/ 下。每一轮先重启 server
go run ./cmd/benchmark -jwt-secret "$JWT_SECRET" \
    -conns 3000 -rooms 10 -msg-rate 0.5 -duration 90s

# 压测进行中另开终端抓 30 s CPU profile
curl -o cpu.prof 'localhost:6060/debug/pprof/profile?seconds=30'
go tool pprof -http=:8081 cpu.prof
```

## 3. 基线：瓶颈在哪

### 3.1 改前的表现

3000 连接下：丢失 7.43%，掉线 12 条，p50 延迟 2 秒，p99 超过直方图上限 10 秒；下行只做到 37.8 万次/s，达不到 44.7 万次/s 的需求。服务端丢弃的原因**全部**是 `client_slow`，没有 `queue_full`。

### 3.2 定位推理链

排查的思路是逐层排除，不靠猜：

| 步骤 | 证据 | 结论 |
|---|---|---|
| ① 看 CPU 花在哪 | 火焰图里 55% 在 `Syscall6`，调用方**全部**是 `WriteMessage` | 大头在"往 socket 写"，不在业务代码 |
| ② 排除广播逻辑 | 广播平均 0.47 ms（161 s ÷ 34.6 万次），`Manager.deliver` 只占 CPU 6–9% | 扇出本身（遍历 map、往 channel 里放数据）不贵 |
| ③ 排除应用层队列 | Send 通道只有 32 格，每条连接每秒约收 150 条，32 格最多攒约 0.2 秒的消息 | 应用层队列攒不出秒级延迟 |
| ④ 秒级延迟藏在哪 | 只剩内核 socket 缓冲区：服务端发送缓冲 + 客户端接收缓冲 | 消息堆在内核里 |
| ⑤ 丢弃原因 | 全是 `client_slow`（Send 满），没有 `queue_full`（广播池满） | 堵在每连接的写出口，不在广播入口 |

**判定：瓶颈是"每条消息一次 write 系统调用"。**

### 3.3 原理：为什么逐条写这么贵

**① 系统调用有固定成本。** 每次 `WriteMessage` 都要做完：用户态切到内核态、拿 socket 锁、走一遍 TCP 发送路径、分配 skb、切回用户态。这些开销和"写 50 字节还是 500 字节"关系不大，是**按次数**付费的。一条弹幕要投给 300 人，就是 300 次系统调用。44.7 万次/s 的下行，意味着每秒 44.7 万次 write。

**② loopback 上 write 更显贵。** 同机压测时，发送方的 write 通常会在同一个调用里顺带跑完接收方协议栈的一部分处理。所以火焰图里算在 write 头上的 CPU，有一部分其实是"对端收包"的成本。这也是单机数字只能做相对比较的原因之一。

**③ 为什么延迟到了秒级：排队论。** 把"每条连接的写出口"看成一个服务台：
- 到达率 λ = 这条连接每秒要收的消息数（约 150 条/s）
- 服务率 μ = WritePump 每秒能写出去的消息数，受 CPU 限制

只要 λ ≥ μ，队列就会一直变长，直到所有缓冲区都塞满：
1. 先塞满内核 socket 缓冲区。这里能放几百 KB，也就是几千条消息，延迟就是这样累积到秒级的。
2. 然后 write 开始阻塞，WritePump 停住，Send 通道也被塞满。
3. `deliver` 往里放不进去，只能丢，于是出现 `client_slow`。
4. 堵得最严重的连接超过写超时被断开，就是那 12 条掉线。

所以**延迟、丢失、掉线是同一个问题的三种表现**：服务率跟不上到达率。

## 4. 优化：WritePump 合并写

### 4.1 改法

WritePump 被唤醒拿到一条消息后，不马上发，而是**非阻塞地把 Send 通道里已经在排队的消息全部取出来**，用 `\n` 分隔（NDJSON）写进同一个 WebSocket 帧，最后 `Close` 时一次性发出。见 [backend/internal/ws/client.go](../backend/internal/ws/client.go)：

```go
w, err := c.Conn.NextWriter(websocket.TextMessage) // 开一个帧
w.Write(payload)
n := 1
drain:
for n < sendBuffer {             // 上限 32 条 = Send 通道容量
    select {
    case more, ok := <-c.Send:
        if !ok { break drain }
        w.Write(newline)
        w.Write(more)
        n++
    default:
        break drain              // 通道空了就发，绝不等待
    }
}
w.Close()                        // 这里才真正调用一次 write
metrics.WSWriteBatch.Observe(float64(n))
```

配套改动：前端 [liveSocket.ts](../frontend/src/utils/liveSocket.ts) 和压测工具都改成按 `\n` 拆帧；单条消息就是"没有换行"的特例，走同一段代码。

### 4.2 为什么不加定时窗口

newplan 原本的设计是"攒 5–10 ms 再发"。最终没有这样做：

- 每条连接每秒约收 150 条。10 ms 窗口平均只能攒 **1.5 条**，却要让**每一条**消息多等最多 10 ms，收益很小，代价是确定的。
- 负载低时窗口里只有 1 条，等于白等。

"取空队列就发"的行为是**自适应**的：
- **闲时**：通道里只有 1 条，立刻发，没有额外延迟。
- **忙时**：WritePump 每次被调度到时，通道里已经积了好几条，合并比例自动上升。

实测数据正好印证了这一点：3000 连接时平均 2.9 条/次；5000 连接时 4.07–4.1 条/次。**负载越大，合并得越多**，不需要调参。

这个思路和数据库的 group commit、TCP 的 Nagle 算法本质相同：用"积压本身"作为攒批的信号，而不是额外设一个时钟。区别在于 Nagle 会为了攒批主动等待，这里从不等待。

### 4.3 前后对比

参数：3000 连接 / 10 房间（每房间 300 人）/ 每连接 0.5 msg/s / 90 s。

| 指标 | 改前 | 改后 |
|---|---|---|
| 丢失率 | 7.43% | 0.01% |
| 运行中掉线 | 12 | 0 |
| p50 / p95 / p99 | 2001 / 7598 / >10000 ms | 138 / 266 / 455 ms |
| 下行��递 | 37.8 万次/s | 44.7 万次/s（= 需求 1490 × 300） |
| server CPU（30 s 采样） | 153.8 s（512%） | 116.8 s（389%） |
| `Syscall6` flat | 85.0 s（55%） | 55.6 s（47.5%） |
| 每次 write 条数分布 | 恒为 1 | 平均 2.9；41% 只带 1 条，59% ≥ 2 条，5% ≥ 8 条 |

### 4.4 原理：为什么 CPU 只降 24%，延迟却降 93%

**① 合并只省掉"按次数付的钱"。** 每次 write 的成本 ≈ 固定开销 + 每字节拷贝成本。合并写把固定开销分摊给了 2.9 条消息，但每字节的拷贝一个字节都没少，因为总字节数没变。所以 write 的 CPU 降了 35%，而不是降到原来的 1/2.9。

**② 延迟对"余量"是非线性的。** 回到 3.3 的排队模型：改前 λ ≥ μ，队列无限增长，只能靠塞满缓冲区、丢消息来止住；改后每条消息的服务成本下降，μ > λ，队列不再堆积，大多数消息到达时前面已经没人排队。排队等待时间在利用率接近 1 时会急剧上升，所以把利用率从"≥ 1"拉回到"< 1"，延迟会断崖式下降。CPU 省下的 24%，恰好越过了这条线。

**③ 客户端也受益。** 帧数少了，压测端 `ReadMessage` 的次数也跟着少，而压测端和服务端在抢同一份 CPU。因此延迟的下降里有一部分来自压测端变轻了。**只看服务端自己的证据**，应以 write 系统调用 CPU 85.0 s → 55.6 s 为准。

## 5. 加压到 5000 连接

### 5.1 第一轮：被测量问题污染（保留作教训）

条件：5000 连接 / 10 房间，已开合并写，server **没有重启**。

| 现象 | 实际原因 |
|---|---|
| 只建成 4094 条，906 条失败 | `connect: cannot assign requested address`：**压测端**本机临时端口耗尽，不是服务端的问题 |
| p50 9.8 s | 直方图上限 10 s，真实值更高 |
| 工具报丢失 13.25% | 服务端这一轮 `client_slow` 只多了约 88 万条，远不到 13%。其余"丢失"是收尾关闭连接时还在内核缓冲区里的**迟到消息**，工具把"迟到"也算成了"丢失" |
| metrics 对不上 | server 没重启，metrics 是两轮的累计值（up 336k，本轮只发了 178k） |

仍然有价值的一点：这一轮平均每次 write 合并 **4.1 条**，比 3000 连接时的 2.9 条更高，是"合并比例随拥塞上升"的又一个证据。

另外，合并写之前做过一轮 5000 连接 / 5 房间，丢失 59.9%，同样有 906 条建连失败，当时没记录失败原因。失败数完全相同，推测是同一个端口耗尽问题（未验证）。

### 5.2 第二轮：修正测量后的干净数据

条件：5000 连接 / 10 房间（每房间 500 人）/ 0.5 msg/s / 约 30 s；已开合并写，压测端轮换源 IP，**server 事先重启**。

**测量可信度**：服务端 up 70641 = 工具 sent；服务端 down 35140504 = 工具 received，两边完全一致。工具算出的丢失率 0.51%，和服务端 `client_slow` 173459 条（0.49%）也对得上。

| 指标 | 值 |
|---|---|
| 建连 | 5000 / 5000，耗时 51 s（200 条/s）；源 IP 在 127.0.0.1–4 之间轮换，绕开单 IP 的临时端口上限 |
| 上行 | 2309 msg/s |
| 下行 | 114.9 万次/s（需求 115.5 万） |
| 丢失 | 0.51%（服务端 `client_slow` 0.49%） |
| 延迟 p50 / p95 / p99 / max | 423 / 1190 / 1729 / 5054 ms |
| 合并 | 8.64M 次 write 发出 35.14M 条消息 = 平均 4.07 条/次；33% 只带 1 条 |
| server CPU（30 s） | 198 s（660%） |
| `Syscall6` | 123 s（62%），几乎全是 write（recvfrom 0.17 s，EpollWait 1 s） |
| `deliver` | 占 CPU 6.8%；一次广播平均 0.5 ms |

这是本机能拿到的最后一组可信数据。

### 5.3 写成本次线性增长

| | 3000 连接（合并后） | 5000 连接（合并后） | 倍数 |
|---|---|---|---|
| 下行消息量 | 44.7 万/s | 114.9 万/s | **2.6×** |
| write 系统调用 CPU | 55.6 s | 123 s | **2.2×** |
| 平均每次 write 条数 | 2.9 | 4.07 | 1.4× |

负载翻倍时，合并比例也跟着上升，每条消息分摊到的系统调用开销在变小。没有合并写的话，这两列的倍数应该一样。

### 5.4 本机的拐点

- 44.7 万次/s（3000 连接）时：p99 455 ms，丢失 0.01%，状态健康。
- 114.9 万次/s（5000 连接）时：p99 1.7 s，丢失 0.5%，开始吃力。

拐点大致在两者之间。再往上加，server 和 benchmark 抢 CPU 的效应会越来越明显，**没法区分瓶颈在哪一侧**，必须换成两台机器。

## 6. 内存

3000 连接时的 heap profile：

| 项 | 值 |
|---|---|
| heap 总量 | 83 MB ≈ **28 KB / 连接** |
| 其中 bufio 读写缓冲 | 40 MB，约占一半。来自 net/http hijack 自带的 4 KB × 2，加上 gorilla 自己分配的缓冲 |
| goroutine 数 | ≈ 2 × 连接数（每条连接一个 ReadPump + 一个 WritePump），没有泄漏 |

注意以下三点：

- newplan 的验收标准"单连接 < 1 KB"，实际只覆盖了 **Send 通道**这一项（32 格 × 24 字节的 slice header = 768 B）。一条连接的总成本约 28 KB，远达不到 1 KB，这个口径在对外讲时要说清楚。
- heap profile **不包含 goroutine 栈**。进程 RSS 会比 83 MB 更高。
- 测这组数据时，upgrader 还没有 `WriteBufferPool`（当时是作为建议提出的）。现在代码里已经加上了（[handler.go](../backend/internal/ws/handler.go)），空闲连接不再占用写缓冲，**需要重测**才能写出新数字。

## 7. Trade-offs

| 得到 | 付出 |
|---|---|
| 系统调用次数随负载次线性增长 | **协议变更**：前端和压测工具都必须按 `\n` 拆帧。任何第三方客户端也要跟着改 |
| 闲时零额外延迟 | **低负载时零收益**：只有 WritePump 被调度得比消息到达还慢时才会合并。41% 的写（3000 连接时）仍然只带 1 条 |
| 不需要调参 | **故障影响面变大**：一帧里有一条消息损坏，前端会逐行解析跳过这一行，但整帧的传输失败会一次丢掉最多 32 条 |
| 单帧最多 32 条，内存有上界 | 单帧变大，客户端单次解析的工作量不均匀 |
| — | 延迟下降的一部分来自压测端变轻（见 4.4 ③），**单机数据会高估服务端的收益** |

不采纳的方案：定时攒批窗口（理由见 4.2）。

## 8. 局限与诚实性说明

- **单机 WSL2**：压测端和服务端争抢 CPU 和内核网络栈，loopback 的开销结构也和真实网卡不同。所有绝对数字只在本机有意义。
- **"下行 114.9 万次/s"是扇出计数**：完整的说法是"5000 连接、每房间 500 人、上行 2309 msg/s 时，完成 114.9 万次/s 的下行投递"，不能说成"114.9 万 QPS"。
- **延迟包含压测端的处理时间**：在高负载下，压测端自己的调度延迟也会算进端到端延迟。
- **单轮数据**：每组条件只跑了一轮，没有做多次取中位数。
- **直方图上限**：当前代码里 `histBuckets = 10001`（上限 10 s）。第 5.2 节那轮的 max 是 5054 ms，没有触到上限；再压更高负载前应把上限调大，否则 p99 会被截断。
- **实验 A / B / C 还没跑**（预序列化、Kafka vs 同步写库、聚合 vs 即时广播），本报告只覆盖合并写这一项。

| 5 | `go tool pprof -peek 'Syscall6$'` 把剩余的系统调用按 write / read / epoll 拆开 | 确认下一步还该不该继续压 write |
| 6 | 补火焰图截图 | 让报告可以直接拿去讲 |

如果两台机器上 write 仍然是大头，可以考虑的方向（**均未验证**）：

- **房间级预合并**：在 BroadcastPool worker 里先把同一房间的多条消息拼好，再扇出。好处是 Send 通道操作和系统调用一起减少；代价是需要一个攒批窗口，要重新权衡延迟。
- **换网络模型**：用 epoll 事件驱动的库（如 gobwas/ws + netpoll）替代"每连接两个 goroutine"。主要收益在内存和 goroutine 数量，对 write 次数帮助不大。
